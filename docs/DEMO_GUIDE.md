# 合同审批智能审查系统 — 端到端演示与验收手册

> 本手册用于**正式验收演示**，可直接照本宣科执行。
> 覆盖场景：软件采购合同、大额销售合同，以及文档加密 / 扫描件模糊两类异常阻断。
> 配套材料：演示合同样本位于 `docs/demo_samples/`。

---

## 零、演示前必读：两条红线

演示过程中，评委通常会追问两个问题。**这两个问题答对了，验收就成了一半。**

### 红线一：大模型不做任何正式业务判定

| 环节 | 谁来做 | 说明 |
|---|---|---|
| 条款语义解析 | 大模型（辅助） | 输出"疑似风险点"，**不带等级** |
| 修改建议初稿 | 大模型（辅助） | 仅作为草稿，法务可改 |
| **风险等级定级** | **规则引擎（唯一）** | 大模型结果进入定级链路前被重新裁决 |
| **违规判定** | **规则引擎（唯一）** | — |
| **任务阻塞判定** | **规则引擎（唯一）** | — |
| **最终审查结论** | **规则引擎（唯一）** | 结论带 SHA-256 哈希，防篡改 |

**佐证话术**：系统的数据结构里，大模型候选对象（`LLMCandidate`）**根本没有** `risk_level` /
`severity` / `decision` 这三个字段。不是"不写"，是"结构上就没有这个位置"。
风险项的 `judge_source` 字段被校验器强制为 `rule_engine`，写入其他值会直接抛异常。

### 红线二：系统只能写"评论"，不能做审批动作

审批系统对本系统**只开放评论接口**，白名单仅两条：

```
允许：/comments 、 /comments/batch
禁止：/approve  /reject  /transfer  /withdraw  /reassign  /sign  /complete  /terminate
兜底：不在白名单内的一切路径，默认拒绝
```

**佐证话术**：这是"默认拒绝"设计 —— 白名单外的路径不是"没实现"，而是"被拦截并留痕"。
模拟审批服务提供 `GET /audit` 可查看全部越权尝试记录；本次交付已实测 **13 项红线检查全部通过**。

### 1.2 一键启动（推荐，约 1 分钟）

```bash
cd deploy/scripts

# 第 1 步：探测基础设施连通性（MongoDB / MinIO / Milvus / 模型服务）
python devctl.py probe

# 第 2 步：初始化数据库 + 向量库 + 自检（首次演示必须执行一次）
python init_all.py

# 第 3 步：一键启动三个应用服务（模拟审批 → 后端 → 前端，按依赖顺序）
python devctl.py start

# 第 4 步：确认三个服务全部就绪
python devctl.py status
```

`status` 理想输出（注意三个服务均为 `[RUN]`）：

```
[RUN ] mock-approval    port=9100    PID=xxxx（由本脚本启动）
[RUN ] backend          port=8000    PID=xxxx（由本脚本启动）
[RUN ] frontend         port=5173    PID=xxxx（由本脚本启动）
```

> **为何强调 `[RUN]` 而不是"端口在监听"**：脚本会校验占用端口的进程名是否属于本项目。
> 若端口被别的程序占用（如 VMware 的 `vmnat.exe` 占了 8000），会显示 `[BUSY]` 并明确报错，
> 而不会误报为"服务已运行"。

### 1.4 规则库总览（演示时可展示）

系统共配置 **34 条**风险规则，覆盖采购 / 销售 / 劳动 / 服务四类合同，按严重度分布：

| 严重度 | 条数 | 映射风险等级 | 典型规则 |
|---|---|---|---|
| `fatal` | 11 | 严重（critical） | 无验收即全款支付、单方无限连带责任、管辖违规 |
| `major` | 17 | 高（high） | 赔偿责任不对等、知识产权责任转嫁、或裁或审并存 |
| `minor` | 5 | 中（medium） | 违约金比例超限、保密期限过短、付款周期过长 |
| `info` | 1 | 低（low） | 大额合同深度复核提示 |

**严重度 → 风险等级映射是确定性映射表，写死在规则引擎中，大模型无法参与。**

## 二、完整演示流程（7 个阶段）

### 阶段 1 — 上传合同 / 创建审查任务

**操作**：进入「合同审查大盘」(`/dashboard`) → 点击「上传合同」→ 选择样本文件。

上传弹窗是**三步串行**流程，界面上会依次显示进度：

| 步骤 | 调用接口 | 说明 |
|---|---|---|
| ① 上传文件 | `POST /api/v1/parse/upload` | 文件进入 MinIO 的 `contract-origin` 桶 |
| ② 创建任务 | `POST /api/v1/tasks` | 生成任务编号，**自动完成差异化路由** |
| ③ 触发解析 | `POST /api/v1/parse/{task_id}/trigger` | 启动 LangGraph 流程 |

**预期结果**：

- 任务出现在大盘列表首行，状态从 `pending` → `parsing` → `reviewing`
- 场景 1 的「路由」列为 `标准审查`；**场景 2 为 `深度复核`**（金额触发）

**对应验收标准**：
- ✅ 支持上传 PDF / DOCX / 扫描件并创建审查任务
- ✅ 金额 ≥ 500 万或高风险合同类型自动进入深度复核
- ✅ 任务状态机正确流转

---

### 阶段 2 — 文档解析（OCR 与条款结构化）

**操作**：点击该任务进入「智能审查工作台」(`/workbench/{taskNo}`)，观察解析进度。

**系统内部动作**（讲解用）：

```
原文抽取 → 文本块构建（带全局字符偏移）→ 段落树还原 → 条款切分 → 条款类型分类
```

条款切分采用**确定性规则**（识别「第X条」「第X章」标记），并记录每条的
`char_start` / `char_end` 全局字符区间。这是"原文 ↔ 结构化结果"双向溯源的锚点。

**为什么必须确定性切分**（评委常问）：
若由大模型切分，同一份合同两次处理可能得到不同区间，导致**溯源失效、审计无法复现**。

**预期结果**：

- 解析完成后，条款列表显示各条款标题与类型（如「第二条 付款方式」→ `payment`）
- 场景 2 应切分出 **10 条条款**（含首部当事人信息）

**对应验收标准**：
- ✅ 支持 PDF/DOCX 文本抽取与扫描件 OCR 识别
- ✅ 条款结构化，条款类型分类正确
- ✅ 字符偏移精确（`full_text[start:end]` 与条款正文严格一致）

---

### 阶段 3 — 智能审查（规则引擎主导）

**操作**：审查自动执行，观察工作台右侧风险卡片逐条出现。

**系统内部执行 10 个节点**：

```
pull_approval_task → parse_document → rule_review
  → (vector_review → llm_review) → risk_merge
  → generate_report → generate_comment → write_comment → audit
```

**关键讲解点 —— 风险融合时发生了什么**：

`risk_merge` 节点把三路结果（规则命中 / 向量召回 / 大模型候选）合并。合并时**强制丢弃**
向量与大模型候选携带的任何等级字段，只保留其证据文本与建议作为「参考内容」。
最终 `risk_level` 字段**只可能来自规则引擎**。

界面上可观察到：**AI 参考项不参与定级**，风险卡片排序为「规则命中优先」。

**预期结果**（严格对齐 1.3 节的实测结论）：

- 场景 1：最终等级 **严重风险**，命中 **5** 条 → 5 张风险卡片
- 场景 2：最终等级 **高风险**，命中 **2** 条 → 2 张风险卡片
- 每张卡片显示：规则编码、风险等级、证据原文（高亮）、修改建议、法律依据

**证据溯源自检**（可现场演示）：点击风险卡片的证据片段，左侧原文视窗自动跳转并高亮到对应位置。
这说明 `char_start` / `char_end` 坐标链路是通的。

**对应验收标准**：
- ✅ 规则引擎完成合规风险识别与定级
- ✅ 命中风险可追溯到规则编码与原文位置
- ✅ 大模型不参与定级（AI 参考项独立标识）
- ✅ 修改建议与法律依据可给法务直接参考

### 阶段 4 — 法务人工复核

**操作**：法务人员逐条查看风险项，可执行两类操作：

| 操作 | 接口 | 说明 |
|---|---|---|
| 编辑风险项 | `PUT /api/v1/review/risk-items/{risk_id}` | 修改风险描述 / 补充说明 |
| 修改推荐条款 | `PUT /api/v1/review/risk-items/{risk_id}/recommend` | 调整建议条款文本 |

> **演示要点（重要）**：法务编辑**不会改变风险等级与判定结论**。
> `set_legal_opinion()` 方法只写 B 类字段（意见、说明），
> **A 类判定字段（risk_level / decision / severity）永不触碰**。
> 这是"法务意见不改判定"红线，已实测验证：写入法务意见后判定字段字节级不变。

**预期结果**：

- 编辑后风险项描述更新，但风险等级、判定结论保持不变
- 修改记录进入审计日志

**对应验收标准**：
- ✅ 支持法务人工复核与批注编辑
- ✅ 人工意见不篡改规则引擎判定（红线）

### 阶段 6 — 回写审批评论（红线演示）

**操作**：确认预览内容 → 点击「回写审批意见」。

| 步骤 | 接口 |
|---|---|
| 回写 | `POST /api/v1/report/{task_id}/comment/write-back` |

**回写请求体只有 4 个字段**（这是红线的物理体现）：

```json
{
  "contract_review_comment": "【合同智能审查意见】...",
  "task_no": "CR-20260919-xxxx",
  "final_risk_level": "critical",
  "risk_count": 5
}
```

> **演示要点**：请求体里**没有任何动作类字段**。系统在构造请求前会执行字段白名单过滤，
> `action` / `approve` / `reject` / `transfer` / `withdraw` / `reassign` / `sign` /
> `complete` / `terminate` / `result` / `decision` 全部被剔除并记录 WARNING 日志。

**现场验证越权拦截**（强烈建议演示，是验收加分项）：

```bash
# 0. 演示前的环境变量（避免本机 HTTP 代理拦截 127.0.0.1）
export NO_PROXY=127.0.0.1,localhost

# 1. 正常评论（白名单）→ 应返回 200
curl -X POST http://127.0.0.1:9100/comments \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer demo-token" \
  -d '{"task_no":"CR-DEMO-001","contract_review_comment":"审查意见","final_risk_level":"high","risk_count":2}'

# 2. 尝试审批通过（黑名单）→ 必须 403，即使 token 合法
curl -X POST http://127.0.0.1:9100/approve \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer demo-token" \
  -d '{"task_no":"CR-DEMO-001","action":"approve"}'

# 3. 查看越权留痕
curl http://127.0.0.1:9100/audit
```

**已实测结果**（本节数据为真实执行所得，非预估）：

| 请求 | 实测结果 |
|---|---|
| `POST /comments`（白名单 + 合法 token） | **200** ✅ |
| `POST /approve`（合法 token） | **403** ✅ |
| `POST /reject` / `/transfer` / `/withdraw` / `/reassign` / `/sign` / `/complete` / `/terminate` | **全部 403** ✅ |
| `POST /approve`（**不带** token） | **403** ✅ |

**`GET /audit` 返回结构**（演示时可投屏）：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "verdict": "警告：发现 11 次越权尝试。审查系统不应调用动作类接口，请检查 approval_guard 是否被绕过。",
    "total": 11,
    "items": [
      {
        "audit_id": "bf5e365c1069",
        "api_path": "/approve",
        "action": "approve",
        "payload": { "task_no": "CR-DEMO-001", "action": "approve" },
        "client_host": "127.0.0.1",
        "authorized": true,
        "rejected": true,
        "reject_reason": "该接口不在评论白名单内..."
      }
    ],
    "allowed_apis": ["/comments", "/comments/batch"],
    "forbidden_actions": ["approve","reject","transfer","withdraw","reassign","sign","complete","terminate"]
  }
}
```

> **注意 `"authorized": true` 与 `"rejected": true` 同时为真** —— 这个细节值得讲解：
> 它证明拦截**不是**靠鉴权做的，而是靠接口白名单。即使攻击者持有完全合法的令牌，
> 动作类接口依然拒绝。这才是"系统能力边界"的正确实现方式。

**预期结果**：

- 正常评论 → `200`，模拟审批系统记录该评论
- 审批动作 → **`403`**，响应体明确提示"本系统仅开放评论接口"并指向 `/audit`
- `/audit` → `verdict` 字段直接给出结论性告警，`items` 列出每次越权尝试


**对应验收标准**：
- ✅ 审查意见成功回写至审批系统

## 三、异常场景演示（阻塞与人工重试）

### 3.0 一键生成异常样本（演示前先跑这个）

异常样本**不要临时找**：加密方式不对、模糊度不够、或文件恰好还能抽出点文字，
都会导致本该阻塞的任务正常通过，在评委面前表现为"系统没识别出异常"。
本目录提供生成脚本，保证每次演示触发的原因码完全一致。

```bash
cd docs/demo_samples
python gen_exception_samples.py
```

生成三个样本（**已实测通过**）：

| 文件 | 触发原因码 | 实测验证 |
|---|---|---|
| `exception1_加密合同.pdf` | `DOC_ENCRYPTED` | 文件含 `/Encrypt` 标记，`is_encrypted=True` ✅ |
| `exception2_模糊扫描件.jpg` | `SCAN_TOO_BLURRY` | 清晰度指标 0.45（清晰文档 > 5），OCR 置信度必然低于 0.6 ✅ |
| `exception3_空白合同.pdf` | `EMPTY_CONTENT` | 抽取正文 0 字符，低于下限 50 ✅ |

> 依赖：`pypdf`、`Pillow`。缺失时脚本会打印明确的 `pip install` 提示，不会静默跳过。

### 3.1 场景 A — 文档加密（`DOC_ENCRYPTED`）

**样本**：`exception1_加密合同.pdf`（口令：`demo-user-pass`）

**演示步骤**：上传该文件 → 创建任务 → 触发解析。

**预期结果**：

- 任务状态变为 **`blocked`**，**不是** `failed`
- 阻塞原因码 = **`DOC_ENCRYPTED`**
- 界面提示：「合同文档已加密，无法抽取正文内容，请上传未加密版本」
- 该任务**不进入重试链路**（属业务事实，非程序错误）

**判定依据**（源码级）：解析节点检测到 `doc_meta.is_encrypted` 为真即抛出
`NonRetryableError(reason="DOC_ENCRYPTED")`，直接置阻塞，**绝不做无意义重试**。

### 3.2 场景 B — 扫描件模糊（`SCAN_TOO_BLURRY`）

**样本**：`exception2_模糊扫描件.jpg`（低分辨率放大 + 高斯模糊 r=8 + JPEG q=12 三重劣化）

**演示步骤**：上传该图片 → 创建任务 → 触发解析。

**预期结果**：

- 任务状态变为 **`blocked`**
- 阻塞原因码 = **`SCAN_TOO_BLURRY`**
- 界面提示：「扫描件识别置信度 0.xxxx 低于阈值 0.6，判定影像模糊，请重新扫描上传」
- 提示中**显示实际置信度数值**（体现不是硬编码固定文案）

**判定依据**：OCR 平均置信度 `< settings.OCR_MIN_CONFIDENCE_THRESHOLD`（默认 **0.6**）即触发。

### 3.4 管理员人工重试（解阻塞）

**操作**：在大盘筛选状态 `blocked` → 选中任务 → 点击「重试」；或调用接口：

```bash
# 方式一：重置为待处理，重新触发审查
curl -X POST http://127.0.0.1:8000/api/v1/tasks/{task_no}/retry

# 方式二：显式指定处理动作
curl -X POST http://127.0.0.1:8000/api/v1/tasks/{task_no}/resolve \
  -H "Content-Type: application/json" \
  -d '{"action":"retry","reason":"已将加密合同替换为未加密版本"}'
```

**两种处理动作**：

| action | 效果 | 适用场景 |
|---|---|---|
| `retry` | 状态置回 `pending`，清空阻塞标记与重试计数，可重新触发审查 | 已提供合格文件 |
| `dismiss` | 状态置为 `failed`（人工确认不再处理） | 确认该合同无法处理 |

**预期结果**：

- `retry` 后：`status = pending`，`blocked_reason = null`，`retry_count = 0`
- 重新上传合格文件并触发解析 → 流程**从解析阶段重新走通**
- 全过程在审计日志中留痕

**对应验收标准**：
- ✅ 三类法定阻断正确触发并置任务为 blocked
- ✅ 阻塞原因为具体原因码而非泛化"失败"
- ✅ 管理员可人工重试 / 驳回
- ✅ 阻塞与重试全过程可审计

## 五、演示话术速查（应对常见追问）

**Q：大模型判断错了怎么办？**
A：大模型的输出在数据结构上就不含等级字段，它只能产生"疑似风险点 + 建议草稿"。所有等级、违规判定、
结论都由规则引擎重新裁决。模型判断错误不会影响任何正式业务结论。

**Q：为什么要有规则引擎？直接用大模型不是更省事？**
A：合同审查是**责任判定**，必须可复现、可审计、可举证。规则引擎的结果是确定性的 ——
同一份合同跑一百次，结论与哈希完全相同。大模型做不到这一点，且无法向上级或审计方
说明"为什么定成高风险"。

**Q：结论会不会被篡改？**
A：结论文本用 `task_id` 加盐做 SHA-256 哈希。任何字符改动都会导致校验失败。已实测验证。

**Q：能不能让系统直接审批通过？**
A：不能，这是设计原则。审批系统只对本系统开放 `/comments` 与 `/comments/batch` 两个接口，
且采用**默认拒绝**策略 —— 白名单外的一切路径（包括我们没预料到的新路径）都会被拦截。
所有越权尝试都会留痕，可在 `/audit` 查看。

**Q：同一份合同里一条规则命中多次，报告会重复列吗？**
A：不会。系统按规则作用域做了去重：条款级规则在不同条款上命中会分别保留（它们是不同的风险事实）；
合同级规则（如必备条款缺失、大额提示）整份合同只保留一条。结论文本中的"命中 N 条"与
风险列表条数严格一致。该一致性有专门的守护测试。

**Q：系统处理失败会一直卡住吗？**
A：不会。三类法定阻断（加密 / 模糊 / 空内容）会立即置为 `blocked` 并给出具体原因码，
不进入无意义重试。程序性异常会按指数退避重试，重试耗尽后置 `blocked(RETRY_EXHAUSTED)`，
交由管理员人工处理。任务状态机保证不会出现"无声卡死"。

## 六、常用运维命令

```bash
cd deploy/scripts

python devctl.py probe                 # 基础设施连通性探测

python init_all.py --only milvus       # 只初始化指定步骤
python init_all.py --recreate          # 重建（会清空数据，非交互环境自动取消）

cd ../backend && python scripts/system_check.py    # 8 分节系统自检报告
bash ../deploy/scripts/verify_mock_approval.sh     # 审批红线验证（须 13/13）
```

### 演示中出问题怎么排查

| 现象 | 首查项 |
|---|---|
| 前端打不开 | `devctl.py status` 看 frontend 是否 `[RUN]`；5173 是否被占 |
| 后端起不来 | 8000 是否被 **VMware `vmnat.exe`** 占用；MongoDB 是否可连 |
| 接口返回 502 | 本机 HTTP 代理拦截了 127.0.0.1，设置 `NO_PROXY=127.0.0.1,localhost` |
| 审查无风险命中 | 规则库是否初始化；`system_check.py` 看 Mongo/Milvus 是否就绪 |
| 回写失败 | 模拟审批服务是否运行（9100）；`/audit` 看是否被拦截 |
| 解析一直不完成 | Milvus / MinIO 连通性；查看 `deploy/runtime/logs/backend.log` |

### 重启后的数据状态说明

> **演示提醒**：模拟审批系统的数据存在**内存**中，重启后清空。
> 因此若演示中间重启了 `mock-approval`，请重新执行一次回写演示。
> 业务数据（MongoDB）与文件（MinIO）则是持久化的，不受影响。
